# handoff v2.0 — 產品需求文件（PRD）

## 背景說明

v1.0 上線後，我們收到了幾位真實使用者（主要是助教與接手實習生）的回饋。整體評價不錯，「交接問題清單」功能特別受好評，有幾位助教反映直接拿去批改學生作業省了不少時間。但隨著使用場景擴大，出現了幾個在 v1.0 設計時沒有預料到的痛點：

1. **掃描範圍太死板**：使用者希望能排除特定目錄（例如 `venv/`、`__pycache__/`、測試資料夾），但現在只要在目錄下就會全掃，產生一堆不相關的雜訊。
2. **風險分數不夠有意義**：100 分的算法對所有地雷一視同仁，但使用者反映他們更想知道「這個專案最集中的問題是什麼類型」，而不只是看一個總分。
3. **沒辦法追蹤特定地雷**：`compare` 指令只能比較兩次掃描的整體分數差異，但無法回答「上次掃到 TODO 有沒有被修掉」這個最直覺的問題。
4. **交接問題清單只能看，不能標記**：幾位使用者說，他們會把清單印出來跟前手逐條確認，確認完的項目希望能在系統裡標記「已釐清」，不然每次重新打開報告又要重看一遍。

以上這些反饋促成了 v2.0 的需求。我們希望在不破壞 v1.0 現有功能的前提下，針對以上痛點進行精準擴充。

## 需求列表

### 需求一：`scan` 指令支援排除規則（修改既有模組）

使用者執行 `scan` 時，希望能透過 `--exclude` 選項指定要跳過的路徑模式，例如 `venv`、`tests`、`migrations` 等。這個排除規則應該要能接受多個值，且支援簡單的萬用字元匹配（例如 `test_*`）。

此外，我們也希望這些排除規則能被持久化為設定值，讓使用者不必每次都重新輸入——也就是說，`config --set` 應該也能設定預設的排除清單。

這個需求會同時影響 `scan` 指令的 CLI 介面、`ScanEngine` 的檔案蒐集邏輯，以及 `Config` 的資料模型。請特別注意：臨時指定的 `--exclude` 與設定檔裡的預設排除清單，兩者的合併邏輯由學生自行決定，但行為必須對使用者透明（例如在報告開頭說明本次實際排除了哪些路徑）。

### 需求二：地雷類型分布統計（修改既有模組）

目前的掃描報告只給一個總風險分數，缺乏「問題集中在哪裡」的洞察。v2.0 希望在掃描報告中新增一個**地雷類型分布區塊**，列出每種 `kind`（`todo`、`missing_docstring`、`naming`、`long_func`、`high_complexity`、`syntax_error`）各有幾顆、佔比多少，並點名哪個類型最嚴重。

Text 格式與 JSON 格式都需要支援這個資訊。JSON 格式中，這份統計應作為 `ScanResult` 的一個新欄位輸出，而不是散落在其他地方。Text 格式的呈現方式（例如表格、長條圖、純文字）由學生自行決定，但必須一眼看出哪種地雷最多。

這個需求主要影響 `reporters.py` 的輸出邏輯，以及 `models.py` 中 `ScanResult` 的資料結構，同時需要考量 `storage.py` 的反序列化是否相容舊有的掃描記錄。

### 需求三：地雷差異追蹤（修改既有模組）

目前的 `compare` 指令只比較兩次掃描的整體統計數字（分數、地雷總數等）。v2.0 希望將比較粒度細化到**個別地雷層級**，能夠呈現：

- **新增的地雷**：在第二次掃描出現、第一次沒有的
- **消失的地雷**：第一次掃描有、第二次沒有的（代表已修復）
- **持續存在的地雷**：兩次都有的

「同一顆地雷」的判斷標準由學生自行定義，但定義必須在設計文件中說明清楚，且要考量到「檔案被重新命名」或「程式碼被搬移導致行號偏移」等邊界情況（不要求完美處理，但要在文件中說明你的選擇與取捨）。

這個需求主要影響 `compare` 指令的邏輯，以及 `reporters.py` 中的 `format_comparison` 方法。

### 需求四：交接問題清單的確認追蹤（全新功能）

v2.0 新增一個 `checklist` 指令，讓使用者能夠針對某次掃描的交接問題清單，逐條標記確認狀態。

基本操作包含：
- `checklist --id <scan_id>`：列出指定掃描的完整問題清單，並顯示每個項目的目前狀態（未確認 / 已確認）
- `checklist --id <scan_id> --resolve <item_index>`：將指定的問題項目標記為「已確認」
- `checklist --id <scan_id> --reset <item_index>`：將已確認的項目改回「未確認」

確認狀態應該要被持久化，重新開啟程式後不應消失。確認狀態的儲存方式（是否附在原有的 ScanResult 上、還是另開一個新檔案）由學生自行決計，但選擇必須在設計文件中說明理由。

這個功能不需要支援即時的多人同步（例如兩個人同時修改同一份清單），但需要在文件中說明你對「同時操作」情境的取捨。

## 驗收標準

以下以使用者可觀察到的行為描述，作為 v2.0 的驗收依據：

**需求一**
- 執行 `python main.py scan ./src --exclude venv --exclude tests`，掃描報告的開頭能看到本次排除了哪些路徑，且 `venv/` 與 `tests/` 下的 `.py` 檔案不出現在掃描結果中
- 執行 `python main.py config --set exclude=venv` 後，後續不帶 `--exclude` 的 `scan` 指令，`venv/` 下的檔案仍然被自動略過
- `config --show` 能顯示目前設定的排除清單

**需求二**
- 執行 `python main.py scan .`，Text 格式報告中出現一個地雷類型分布區塊，能看出每種類型的數量，且最多的類型有明顯標示
- 執行 `python main.py scan . --format json`，輸出的 JSON 中包含一個可機器讀取的地雷分布統計欄位，欄位結構清楚（例如 `{"todo": 3, "naming": 7, ...}`）
- 執行 `python main.py report --id <舊版掃描ID>`，程式不應崩潰，即使舊紀錄沒有分布統計欄位

**需求三**
- 執行 `python main.py compare 1 2`，輸出中除了原有的整體比較外，能額外看到「已修復的地雷」與「新增的地雷」各自的清單，而不只是數字
- 若兩次掃描結果完全相同，輸出應明確告知「無新增或修復的地雷」
- 「已修復的地雷」在 Text 格式下應有明顯的視覺區隔（例如標示 `[FIXED]`）

**需求四**
- 執行 `python main.py checklist --id 1`，能列出第 1 次掃描的所有問題清單，每條前面有編號，並顯示是否已確認
- 執行 `python main.py checklist --id 1 --resolve 2`，能將第 2 條標記為已確認；再次執行 `checklist --id 1` 時，第 2 條顯示為已確認狀態
- 關閉程式後重新執行 `python main.py checklist --id 1`，確認狀態仍然保留
- 對不存在的 `scan_id` 執行 `checklist`，應輸出清楚的錯誤訊息並以非零退出碼結束
